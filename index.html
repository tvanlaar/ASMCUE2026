Reproducibility and Publication Notes

Why this matters: A reproducible analysis includes enough information for another researcher to understand and repeat the workflow.

Galaxy histories help document an analysis by preserving the input files, tool outputs, tool settings, and relationships among datasets. However, a history is only useful for reproduction if the important details are recorded and preserved.

Record these details

  • Input data: Record the sample name, sequencing files, read type, and source of the data.
  • Galaxy information: Record the Galaxy server, history name or ID, workflow name, and date of analysis.
  • Tool versions: Record the exact version of every tool used, including FastQC, fastp, SPAdes, QUAST, CheckM2, Barrnap, Prokka, and BLAST.
  • Parameters: Record important settings such as quality thresholds, minimum read lengths, assembly options, organism or database selections, and filtering cutoffs.
  • References and databases: Record the reference genome, database, database version, or taxonomy database used for each analysis.
  • Output files: Preserve the important reports, assemblies, annotation files, extracted sequences, and BLAST results.

Before publishing

Review the complete Galaxy history and confirm that the files and settings needed to understand the analysis are still available. Export or share the history when appropriate, and include the relevant software versions, parameters, filtering thresholds, and database information in the Methods section.

Workshop reminder: If you think you may publish your analysis, record the exact tool versions and settings while you work rather than trying to reconstruct them later.

1. Getting the Reads into Galaxy

Purpose: Upload paired-end Illumina reads and organize them into a paired collection for downstream analysis.

Short-read Illumina sequencing files should be demultiplexed, with one set of files for each sample. Paired-end files should be labeled with R1 and R2 in their filenames. If your files are organized this way, they are ready to upload.

Once the reads are uploaded, select both files and choose Auto Build List to create a paired collection containing the forward and reverse reads.

What to check

  • Confirm that the forward and reverse reads belong to the same sample
  • Confirm that the files are paired as R1 and R2
  • Use the paired collection for tools that require paired-end reads

2. Quality Assessment and Quality Control

Purpose: Assess whether the sequencing reads are suitable for downstream analysis.

Now that the reads are in Galaxy, use FastQC to investigate the overall quality of the sequencing reads.

You can examine the FastQC results by downloading the report or viewing it directly within Galaxy.

What to look for in the FastQC report

  • Per-base sequence quality
  • Adapter content
  • Per-base N content
  • Warnings or failures that may require investigation

FastQC is a screening tool. A warning or failure does not automatically mean that the sequencing data are unusable. The report identifies patterns that should be evaluated in the context of the experiment and library preparation.

3. Read Trimming with fastp

Purpose: Remove or trim problematic portions of the reads before genome assembly.

We can use fastp to preprocess the reads before assembly. Depending on the settings, fastp can remove adapter sequences, trim low-quality bases, filter reads containing too many ambiguous bases (Ns), and discard reads that are too short. It also produces a report summarizing the changes made to the read set.

Once the reads have been trimmed, you will have cleaned read files and fastp results files.

What to look for in the fastp report

  • The number of input reads
  • The number and percentage of reads that passed filtering
  • The number of bases retained
  • Changes in read length and GC content
  • Adapter and quality-trimming statistics

The fastp report can provide useful information for documenting the read-processing methods and results.

You can run FastQC again on the trimmed reads as an additional quality check. If the original reads were already high quality, the second FastQC report may look very similar; that result is still informative.

4. Genome Assembly with SPAdes

Purpose: Assemble the cleaned sequencing reads into longer genomic sequences called contigs.

Use SPAdes to assemble the sequencing reads. Select the trimmed paired reads as the input so that only the processed reads are used for the assembly.

What SPAdes produces

  • A FASTA file containing assembled contigs
  • Assembly statistics and other output files
  • Potentially, a scaffold file in addition to the contig file

A contig is a continuous assembled DNA sequence. A scaffold is made by linking contigs using paired-read information and may contain gaps represented by Ns.

5. Filtering Short Contigs

Purpose: Remove very short sequences that are more likely to represent assembly artifacts or low-confidence fragments.

Use the FASTA filtering tool to retain contigs at or above the selected length threshold. For this analysis, retain contigs that are at least 500 bp long.

This filtering step creates a new FASTA file; it does not alter the original SPAdes assembly. Keep the original assembly available for comparison and documentation.

Important note

A 500-bp cutoff is a quality-filtering choice, not a universal biological requirement. Short contigs can sometimes contain real biological features, so the cutoff and its effects should be documented for publication.

6. Assembly Assessment with QUAST

Purpose: Evaluate the structure and continuity of the genome assembly.

Use QUAST to calculate assembly statistics such as the number of contigs, total assembly length, GC content, longest contig, and N50.

The minimum contig-length setting in QUAST affects which contigs are included in the statistics. It does not physically remove contigs from the FASTA file. The actual filtering was performed in the previous step.

What to look for

  • Total assembly length: The combined length of all contigs included in the assembly, reported in base pairs.
  • Number of contigs: The total number of separate assembled DNA sequences. Fewer contigs generally indicate a less fragmented assembly.
  • Longest contig: The length of the largest individual contig in the assembly.
  • N50: The contig length at which contigs of that length or longer contain at least 50% of the total assembly length. A larger N50 generally indicates a more contiguous assembly.
  • GC content: The percentage of bases in the assembly that are guanine (G) or cytosine (C). This can be compared with the expected GC content of the organism.

7. Genome Quality Assessment with CheckM2

Purpose: Estimate the completeness and contamination of the assembled genome.

CheckM2 evaluates the quality of an assembled genome by estimating how complete the genome is and whether it contains evidence of contamination. Use the filtered contigs from the previous step as the input.

Running CheckM2 in Galaxy

Interpreting the CheckM2 results

What to look for

  • Completeness: The estimated proportion of the expected genome that is present. Higher completeness generally indicates that fewer expected genes are missing.
  • Contamination: The estimated proportion of the assembly that may come from other organisms or additional genomes. Lower contamination is preferable.
  • Overall quality: Interpret completeness and contamination together rather than judging the assembly from one value alone.

CheckM2 provides estimates rather than absolute measurements. These results should be considered alongside the assembly statistics from QUAST, the sequencing quality results, and the biological context of the sample.

8. 16S rRNA Identification with Barrnap

Purpose: Identify the 16S rRNA gene and use its sequence for a preliminary identification of the assembled bacterium.

Use Barrnap with the assembled contigs as input. Barrnap identifies ribosomal RNA features, including 5S, 16S, and 23S rRNA genes.

Running Barrnap in Galaxy

What to look for in the Barrnap results

  • Features labeled 16S_rRNA or 16S ribosomal RNA
  • The number of 16S rRNA copies detected
  • The lengths and locations of the predicted rRNA genes

Extract the predicted 16S rRNA sequence as a FASTA file before beginning the BLAST search.

Searching the 16S rRNA Sequence with BLAST

What to look for in the BLAST results

  • Query coverage: The percentage of the input 16S sequence included in the alignment
  • Percent identity: The percentage of aligned bases that match the database sequence
  • E-value: The likelihood that the alignment occurred by chance; smaller values indicate more statistically significant matches
  • Organism names and accession numbers: The identities of the closest database matches and the records used for comparison

A strong 16S match can provide a preliminary identification, but 16S rRNA often cannot distinguish between very closely related bacterial species. Interpret the result together with the genome assembly, annotation, and other taxonomic evidence.

9. Genome Annotation with Prokka

Purpose: Identify and annotate protein-coding genes, rRNA genes, tRNA genes, and other genomic features.

Prokka uses several software tools and reference databases to annotate a bacterial genome. It produces multiple output files that describe the predicted features and provide sequences and formats for downstream analyses.

Running Prokka in Galaxy

Important Prokka settings

Use the filtered assembly as the input for Prokka. Leave the options to disable rRNA and tRNA searches unchecked. This allows Prokka to run its standard rRNA and tRNA prediction steps.

Understanding the Prokka outputs

  • .gbk: An annotated GenBank-format file containing the assembled sequences and predicted genomic features. This is useful for viewing the annotation and preparing for downstream submission, although additional preparation may be required for GenBank submission.
  • .gff: The main annotation file. It records the locations and descriptions of predicted genes and other features on the contigs.
  • .tsv: A tab-separated annotation table containing information such as feature type, location, gene name, product, and functional annotations.
  • .faa: FASTA sequences of the predicted proteins translated from protein-coding genes.
  • .ffn: FASTA nucleotide sequences of predicted features, including protein-coding genes, rRNA, tRNA, tmRNA, and other RNA features.
  • .txt: A summary of the annotation results, including the numbers of predicted coding sequences, rRNAs, tRNAs, and other features.
  • .log: A record of the Prokka run, including software settings and information useful for documenting the analysis.

What to look for

  • How many protein-coding genes were predicted?
  • Were rRNA and tRNA features identified?
  • How many genes were assigned functional names?
  • How many features remain annotated as hypothetical proteins?
  • Which output files would be useful for future analyses or publication?
